# 项目数据文档 · 编写指令

> ⚠ 本文件是**给 agent 的指令模板**，不是项目介绍本身，不参与网站构建。
> 用法：把下面「以下为指令正文」之后的全部内容复制给 agent，并把 `<项目根目录>` 换成实际路径。
> 生成物放在 `docs/其他项目介绍/<slug>-数据.md`，供人工评审后并入 `app/data/projects.js`。

## 以下为指令正文

# 任务：为一个项目编写「项目展示数据文档」

你要为个人网站 `/projects`（项目展示页）编写一份**项目数据文档**。文档要产出两块内容：

1. **可读文档**（Markdown）：分节叙述，给人看、给人改；
2. **数据块**（JS 字面量）：放在文末，可直接粘贴进 `app/data/projects.js`。

## 一、先读什么

| 读什么 | 在哪 | 用途 |
| --- | --- | --- |
| 目标项目的报告 / 源码 | `docs/其他项目介绍/`，或 `<项目根目录>` | **唯一**的事实来源 |
| 现有格式样例 | `app/data/projects.js` 的第一条（CNtactic） | 照着它的颗粒度写 |
| 字段含义与渲染规则 | `docs/modules/page-projects.md` | 别写出页面渲染不了的形状 |
| 站点约定 | `docs/README.md`、`docs/02-design-system.md` | 视觉语言、命名、字数习惯 |

读目标项目源码时，按这个优先级找料：`README` → `ARCHITECTURE` / `docs/` → 数据库 migration → 路由注册文件 → CI / 配置文件 → 提交记录里带「fix / 修复 / 坑」的条目。

## 二、输出格式：字段清单

每个项目必须填满 A/B/C 三组，D 组尽力填。

### A 组 · 身份与时间

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `slug` | string | 英文小写 + 连字符（如 `cntactic`）。**它是媒体文件的匹配键**，一旦定下不要改 |
| `title` | string | 展示用中文/原文标题 |
| `kind` | enum | `platform`（多人协作平台）/ `webapp`（单机 Web 应用）/ `desktop`（桌面应用）/ `tool`（脚本或工具） |
| `period` | `{ from, to }` | `'YYYY-MM'` 格式。**只能从源码/报告里找到证据才填**，找不到写 `null` |
| `status` | enum | `wip`（进行中）/ `shipped`（已交付可用）/ `archived`（已归档） |

### B 组 · 定位与读数

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `summary` | string | 一句话定位，**60–110 字**。说清「给谁用、解决什么、怎么做」 |
| `role` | string | 我在这个项目里的角色与负责范围（30–60 字） |
| `metrics` | `[{ label, value }]` | **2–4 项**，只放可核实的量。⚠ 技术栈名称不属于读数 |
| `stack` | `[{ group, items[] }]` | 技术栈按层分组，如 `{ group: '前端', items: ['Vue 3.5', 'Pinia'] }` |
| `tags` | string[] | **只能从下方白名单里选**，3–6 个，供页面做筛选 |

`tags` 白名单（不得自行新增，需要新增必须单独提出）：

- 领域：`电竞` `教育` `效率` `数据` `内容`
- 形态：`平台` `Web 应用` `桌面应用` `工具`
- 技术族：`Vue` `React` `Go` `Node` `Rust` `Python` `PostgreSQL` `MySQL` `SQLite`

### C 组 · 图纸槽位（`blueprints`）

`blueprints` 是**以槽位名为键的对象**，不是数组 —— 顺序由槽位决定，不由你排。

| 槽位 | 编号 | 这张图要讲什么 | 渲染 kind |
| --- | --- | --- | --- |
| `shot` | 01 | 真实界面截图（**只写文件路径**，不画） | 图片 |
| `arch` | 02 | 系统全景 / 分层架构：有哪些参与者、怎么分层、数据往哪流 | `layout` |
| `flow` | 03 | 一条核心业务链路（端到端，不是功能罗列） | `pipeline` |
| `data` | 04 | 数据模型 / 关键表与关系 | `layout` |
| `shell` | 05 | 应用外壳与导航（**仅桌面端应用**填） | `app` |
| `ops` | 06 | 运行与部署形态（几个进程、怎么起、依赖什么） | `layout` |

每张图统一三个字段：

- `caption`：一句话说这张图在讲什么（≤20 字）
- `notes`：图内要点 2–3 条（每条 ≤30 字）
- `dimension`：尺度小签（如 `5 个服务 · 1 个人`、`上传 → 异步解析 → 回写`）

**没有的槽位直接不写**，不要为凑数编一张图。缺了哪个槽位在文档里单列说明。

### D 组 · 叙事（用户最想看的部分）

| 字段 | 类型 | 条数 | 说明 |
| --- | --- | --- | --- |
| `highlights` | `[{ n, title, text }]` | 3–4 | 做法 → 结果。见下方 §四 |
| `pitfalls` | `[{ label, symptom, cause, fix }]` | ≥2 | 真实踩过的坑。见 §五 |
| `reflections` | `[{ label, text }]` | 1–3 | 反思：做对了什么、如果重做会怎么改 |
| `principles` | string[] | 2–3 | 设计理念，一句一条（≤40 字） |
| `nextSteps` | `[{ label, text }]` | 1–3 | 已知短板与下一步计划 |

`label` 统一成 `'PITFALL 01'` / `'REFLECT 01'` / `'NEXT 01'` 这种等宽小签格式。

## 三、数字怎么数（口径必须写出来）

`metrics` 是最容易编造的地方。每个数字都要用**可复述的方法**数出来，并在文档里注明口径：

| 想数的东西 | 建议做法 | 口径必须写清 |
| --- | --- | --- |
| 代码行数 | `git ls-files` 后逐文件统计，排除 `node_modules`、锁文件、生成物 | 统计了哪些目录、排除了什么 |
| 服务 / 进程数 | 数独立的启动入口或部署单元 | 是否含数据库等外部依赖 |
| 业务表数 | 数 migration / 建表语句 | 是否含关联表、日志表 |
| 接口 / 路由数 | 数路由注册文件 | 是否合并了 module 级注册 |
| 测试用例数 | 跑一次测试命令取报告 | 单测还是含 E2E |
| 版本号 | 读 `package.json` / `Cargo.toml` / `tauri.conf.json` | — |

数不出来就不写。**宁少不假。**

## 四、亮点怎么写

每条亮点是一个**迷你技术故事**，结构固定：

```
title  ≤10 字，名词短语，说清「做了什么」
text   ≤90 字，句式：问题/约束 → 做法 → 结果
```

质量要求：

- 至少一条要写出**被否掉的替代方案**（「原本用 X，因为 Y 换成 Z」）—— 这最能体现工程判断。
- 至少一条要写出**可核实的收益**（性能、成本、可维护性、解除的耦合），不要写「提升了体验」这种空话。
- 禁止把亮点写成技术栈罗列或功能清单。判断标准：**每条都能被追问「为什么这么做」**。

## 五、踩坑怎么写

`pitfalls` 是本页最有价值的部分，也最容易写假。硬性要求：

- 每条必须来自**真实的**排障记录：报告里的「已知问题」章节、提交记录、issue、调试日志。
- 三段结构缺一不可：
  - `symptom`：**观察到的现象**（要具体到能复现，如「接口返回 200 但列表永远为空」）
  - `cause`：**根因**（不是「配置错了」，而是「MySQL 要求 LIMIT 绑定 BIGINT，驱动把 JS number 当 DOUBLE 发」）
  - `fix`：**怎么修的** + 是否顺带修掉了同类问题
- 禁止写「常识性坑」（如「记得处理空指针」）—— 那是教科书，不是你的经历。
- 痛点越具体越好，**能暴露真实难度的坑才是加分项**。

## 六、红线（违反任意一条即不合格）

1. **只写报告/源码里出现过的事实。** 每条结论都要能指出出处（文件 + 章节/行）。
2. **禁止编造**：用户量、并发量、DAU、性能提升百分比、崩溃率、覆盖率涨幅 —— 除非报告里有 benchmark 记录。
3. **`metrics` 里不得出现技术栈名称**（「前端 Vue 3.5」不是读数）。
4. **不得美化短板**：`nextSteps` 要照实写。诚实反而加分。
5. **不得跨项目搬运**：A 项目踩过的坑不能写进 B 项目。
6. **无法确认的字段**：写 `null`，并在文档末尾用「待确认」单列出来。**不要猜。**

## 七、交付要求

1. 文件路径：`docs/其他项目介绍/<slug>-数据.md`
2. 文档结构：`## 项目概览` → `## 读数与口径` → `## 图纸` → `## 亮点` → `## 踩坑` → `## 反思与理念` → `## 下一步` → `## 待确认` → `## 数据块`
3. 文末必须有一个 ```js 代码块，内容是一个完整对象，**可直接粘贴进 `app/data/projects.js` 的 `projects` 数组**。
4. 长度控制：`summary` ≤110 字、每条 `highlight.text` ≤90 字、每条 `pitfall` 三段各 ≤80 字。超了就是没提炼。

## 八、完成后自检（逐条报告结果）

- [ ] 每个数字都能指出出处（文件 + 章节/行），并写明了统计口径
- [ ] `metrics` 里没有任何技术栈名称
- [ ] 每条亮点都是「问题 → 做法 → 结果」，且至少一条写了被否掉的替代方案
- [ ] `pitfalls` ≥2 条，每条三要素齐全，且都能追溯到真实记录
- [ ] 全文没有出现用户量 / 并发量 / DAU / 未记录的性能百分比
- [ ] `tags` 全部来自白名单
- [ ] `blueprints` 只填了真实存在的图，缺位已在文档里说明
- [ ] 报告里没出现过的事实，一条都没写
- [ ] 文末代码块是合法 JS，字段名与本文档 §二 完全一致
- [ ] 「待确认」一节已列出所有拿不准的字段
