## 一、一句话定位（简历"项目名称"下方第一行）

> 基于 **Tauri 2（Rust）+ React 19 + TypeScript** 的跨平台桌面效率应用，
> 内置**沙箱化插件系统**与**计划生成器**，覆盖任务/习惯、情绪记录、统计分析与数据备份，
> 前端约 1.9 万行 TS/TSX + Rust 后端约 700 行，**120 个单元测试全绿，CI 全自动化**。

备选更短的版本：

> Tauri 2 + React 19 桌面应用：自研沙箱插件系统（能力声明 + 权限门 + postMessage 来源校验）、
> 带版本迁移的 SQLite 数据层、全量备份/恢复，120 用例单测 + GitHub Actions CI。

## 二、技术栈（按层次写，别堆名词）

| 层 | 选型 | 一句话理由（面试可讲） |
|---|---|---|
| 桌面框架 | Tauri 2（Rust） | 相比 Electron 安装包/内存小一个量级；Rust 侧负责 SQLite 与系统能力 |
| 后端 | Rust + rusqlite + r2d2 连接池 | 11 个 IPC 命令，单一入口（lib.rs），命令层薄、数据层收敛 |
| 前端 | React 19 + TypeScript + Vite + Tailwind | 函数组件 + 自定义 Hook，无重型状态库，按 feature 分域 |
| 路由 | react-router（HashRouter） | Tauri 自定义协议下 Browser 路由刷新/深链会 404，桌面端必须 Hash |
| 数据 | SQLite（迁移机制）/ IndexedDB（计划器）/ localStorage（设置） | 按数据形态分存储，不做一刀切 |
| 测试 | Vitest（node env，DOM/IPC 手工桩） | 12 文件 120 用例，安全与数据咽喉优先覆盖 |
| 工程 | ESLint 9 flat config + GitHub Actions CI + 版本单一真源脚本 | typecheck → lint → test → build 全自动化 |

## 三、核心亮点（简历 bullet 素材，按含金量排序）

**1. 设计并实现沙箱化插件系统（最值钱，放第一条）**
- 插件以声明式清单（TOML）描述能力：`theme / page / data / code` 四类；
- 页面类插件运行在 **iframe 沙箱**中，通过 postMessage 与宿主通信；
- 通信层做**消息来源校验**（`event.source === iframe.contentWindow`），伪造消息必须先进入该 iframe；
- 数据访问走**权限门**：插件只能读写清单声明过的 namespace，越权操作全部拒绝（有单测覆盖每一条拒绝分支）；
- 安装期校验 `minCoreVersion/maxCoreVersion` 与宿主核心版本兼容，不满足直接拒绝安装。

**2. Rust 数据层：迁移机制 + 增量更新 + 注入防护**
- 以 SQLite `PRAGMA user_version` 驱动**顺序迁移表**：新库建表即最新结构，旧库逐版本升级，
  彻底取代"删库重建"，加字段不再需要用户清数据；
- 任务更新用**列白名单 + 占位符参数化**的 `patch_task`：键名只作查表、值全部走绑定参数，
  从结构上排除 SQL 注入；一次 IPC 完成增量更新，替代"先全量读、改完再全量写"的模式；
- 情绪数据从独立表迁移至插件命名空间数据（`plugin_data`），消除"同一份数据两处存储"的一致性隐患。

**3. 全量备份/恢复（数据完整性工程）**
- 一个入口聚合 5 类数据：SQLite 任务、插件命名空间数据、IndexedDB 计划/资源、应用设置、用户资料；
- 恢复策略是**合并而非清库重建**：任务按"标题+创建时间"去重追加，插件数据按 key upsert，
  设置字段级合并——用户导错文件也不会丢现有数据；
- 覆盖 Tauri（SQLite/IPC）与浏览器（localStorage/IndexedDB）双运行时。

**4. 双后端存储抽象**
- 同一套业务代码跑在桌面（Tauri IPC → SQLite）与浏览器（localStorage/IndexedDB）两种运行时，
  以 `isTauriRuntime()` 在数据层做唯一分叉点，业务组件不感知差异。

**5. 工程化与质量**
- Vitest **120 用例**（安全权限门、IPC 字段映射/降级、迁移往返、备份合并语义全部有断言）；
- ESLint 9 flat config：error 级只留 `rules-of-hooks` 等两条硬规则，warning 不阻塞 CI——
  **门禁要有牙但不咬存量代码**，这是刻意做的口径取舍；
- CI（GitHub Actions）：版本一致性检查 → typecheck → lint → test → build；
  版本号以 `tauri.conf.json` 为单一真源，脚本自动同步三处；
- 依赖治理：一次性移除 **10 个零引用依赖**，前端 API 层从 417 行精简到 127 行。

**6. 产品功能面（证明你能做完整应用而不只是 demo）**
- 任务/习惯打卡、情绪日记、统计页（与上一等长周期真实同比，非占位数据）、
  向导式计划生成器（多步表单 + 资源库 + IndexedDB 持久化）、插件管理器、设置与备份。

## 四、面试口述版

**30 秒版：**
> 这是我独立开发的跨平台桌面应用，解决"任务、情绪、计划"三类个人数据的统一管理。
> 技术上选 Tauri 2 而不是 Electron，Rust 侧管 SQLite，前端 React 19。
> 我最投入的是插件系统：插件用声明式清单描述能力，跑在 iframe 沙箱里，
> 数据访问有权限门隔离，通信有来源校验——安全模型是这套架构的核心。
> 数据层做了版本迁移机制和全量备份/恢复，120 个单测加 CI 保证质量。

**2 分钟版（按"架构 → 安全 → 数据 → 质量"四段讲）：**
1. **架构**：为什么 Tauri——包体积和内存对比 Electron 的量级差异；Rust 只暴露 11 个 IPC 命令，
   命令层薄、业务在前端，职责边界清楚。
2. **安全**：插件分四类能力，只有 page/code 类需要沙箱；iframe + postMessage，
   校验 `event.source` 防伪造；数据按 namespace 隔离，权限门在数据层统一拦截。
   讲的时候要能说出"为什么来源校验够用、什么时候不够（远程插件没有 token 握手，这是已知边界）"。
3. **数据**：`user_version` 顺序迁移（举 moods 表 → plugin_data 的真实迁移例子）；
   `patch_task` 列白名单防注入；备份合并恢复的幂等思路。
4. **质量**：为什么测试用 node 环境而不是 jsdom——被测的是逻辑咽喉（权限门、字段映射、迁移），
   DOM 用手工桩注入更快更稳；lint 口径的取舍。

## 五、面试追问预案（写简历前自测）

| 可能的追问 | 你的答案要点 |
|---|---|
| 为什么不用 Electron？ | 包体积（Tauri 复用系统 WebView）与内存占用；代价是要处理各平台 WebView 差异，桌面端用 HashRouter 规避路由 404 就是实例 |
| patch_task 怎么防注入？ | 列名走 `PATCHABLE_COLUMNS` 白名单查表（永不拼接用户输入），值用 rusqlite 占位符绑定；JSON null 语义 = 置空列 |
| 迁移机制怎么设计的？ | `MIGRATIONS` 数组 + `user_version` 游标，只允许末尾追加；`guard` 声明"新库建表已含该列"避免重复 ALTER |
| 沙箱真的安全吗？ | 边界要说实话：本地代码插件可信度靠清单声明 + 权限门；远程 url 插件能加载任意页面，来源校验保证消息只能从该 iframe 发出，但没有 token 握手（已列为后续项） |
| 为什么备份用合并不用覆盖？ | 用户可能拿旧备份恢复到新数据上，清库重建会丢新增数据；合并以"标题+创建时间"为业务幂等键 |
| 测试为什么不用 jsdom？ | 被测对象是纯逻辑（权限门/映射/迁移），node env 启动快（全套 1s 内）；依赖 DOM 的模块由测试注入桩对象 |
| 遇到的最大坑？ | 可讲：插件卸载后宿主回调同步抛异常导致 catch 不到（改为统一 rejected promise）；或 hooks 实验性 lint 规则 32 个 error 的口径取舍 |

## 六、诚实边界（面试别吹过）

- 个人项目，没有真实多用户/高并发场景——**不要**往分布式、高可用上靠；
- 无乐观锁、无 Prettier、覆盖率未统计、远程插件 token 握手未做——被问到直接承认并说明取舍理由，
  "知道边界 + 有取舍依据"比"全都说做了"更加分；
- 心情数据迁移是一次性 SQL，不是通用 ETL；备份不含头像图片本体。
