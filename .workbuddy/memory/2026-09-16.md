## 修复：浏览器环境下 Tauri API 未守卫导致的控制台报错

### 现象与根因

浏览器打开 `http://127.0.0.1:1420` 时控制台报：

```
useUserProfileTauri.ts:44 Failed to load user profile:
TypeError: Cannot read properties of undefined (reading 'invoke')
useUserProfileTauri.ts:58 Failed to save user profile: （同上）
```

根因：`src/hooks/useUserProfileTauri.ts` 在**模块顶层静态 import** `@tauri-apps/plugin-fs`，
并**无条件调用** `exists/readTextFile/writeTextFile/readFile/mkdir/remove`。
该插件的实现是 `window.__TAURI_INTERNALS__.invoke(...)`，浏览器里这个全局不存在 → `invoke` 是
`undefined` → 调用即抛。项目其它 Tauri 调用点（`dataStore.ts` / `storage.ts` / `backupService.ts`）
都已经有 `isTauriRuntime()` 守卫 + 动态 import + localStorage 兜底，**只有这个 hook 漏了**。

### 改动

- **`src/hooks/useUserProfileTauri.ts`（重写）**
  - 新增 `profileStore` 适配层，把 4 个操作（readProfile / writeProfile / readAvatar /
    writeAvatar / removeAvatar）收敛到一处，内部分 `isTauriRuntime()` 两分支并**动态 import**
    plugin-fs；浏览器分支走 localStorage。
  - 键名沿用项目约定：`mood-task:user-profile:v1`、`mood-task:user-avatar:v1`（头像存 data URL）。
  - 顺带修掉旧实现的几个隐患：`normalizeProfile()` 对磁盘/localStorage 的不可信内容做归一化；
    data URL ↔ Uint8Array 转换分批 `fromCharCode`（防大数组爆栈）；
    头像读取失败不再用闭包里过期的 `userProfile` 回写；

  验证告警是否消失要用**全新 `open`**，不要用 `reload`。
- `agent-browser storage local` 比 `eval localStorage.getItem(...)` 更省事，且不受 shell 引号影响，

## 诊断：桌面端 B 站 / SearXNG 报错的真因（重要结论）

用户跑的是桌面端 + SearXNG（docker `-p 8888:8080`，named volume `searxng:/etc/searxng`），
但控制台仍报 CORS + 403。curl 实测定论：

- `GET localhost:8888/` → 200；`GET /search?q=test`（html）→ 200；
  `GET /search?q=test&format=json` → **403**（SearXNG 新版默认 `search.formats` 只有 html，
  json 未加白名单直接 403；`/config` 里 `limiter.enabled=false` 排除了限流）。
  **"CORS 拦截"是表象：服务端 403 的响应上没有 CORS 头，浏览器统一报成 CORS 违规。**
- B 站 `wbi/search/type?search_type=video` 用 curl（带 UA + Referer）**无需 wbi 签名**即返回
  `code:0`，连打 3 页均 20 条；而旧路径 `/nav` 取 img_key/sub_key（浏览器里被 CORS+风控拦 403）
  是前端搜索必挂的根因。
- `cargo tree -e features -i reqwest` 发现 tauri 传递引入的 reqwest **只启了 json+stream，
  没有任何 TLS feature** → 直接 `reqwest::get` https 会失败，必须显式声明。

### 第二个坑：200 了但 results=0

`/search?format=json` 返回 200 却 0 条结果。逐层排查：

- `/config` 看默认启用的 general 引擎：`wikipedia / wikidata / duckduckgo / google cse /
  lingva / brave` —— **全是被墙的**，每个都白等 3s 超时；
- `docker logs` 拿到确凿错误：`duckduckgo/wikipedia/wikidata: engine timeout`、
  `brave: DNSError`、`google cse: ConnectionError`。

于是改 `settings.yml` 的 `engines:` 段（`use_default_settings: true` 下按 name 合并覆盖），
逐个隔离测试后定论：

| 引擎 | 结论 |
|---|---|
| **360search** | ✅ **唯一稳定可用**：4 次查询全 4 条，质量高（菜鸟教程/慕课网/脚本之家） |
| quark | ⚠️ 间歇（有时 8 条，有时无响应）→ 关 |
| baidu | ❌ **首查即 CAPTCHA**（`SearxEngineCaptchaException`，suspended 1 小时）→ 关 |
| bing | ❌ HTTP 200 但 0 条（被重定向到 cn.bing 变体，解析器扑空）→ 关 |
| sogou | ❌ 引擎代码 bug：`AttributeError: resp.next_request`（`sogou.py:56`）→ 关 |
| duckduckgo/brave/wikipedia/wikidata/google cse/lingva | ❌ 被墙 → 关 |

**终验：只留 360search，4 次查询 4/4 稳定成功、合计 16 条、零无响应引擎。**

> 教训：SearXNG 「HTTP 200 但没结果」几乎总是引擎问题，不是配置格式问题。
> 排查顺序：`/config` 看 enabled 引擎 → `docker logs searxng | grep engine` 看超时/报错
> → 用 `&engines=xxx` 单引擎隔离测试。
